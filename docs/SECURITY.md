# Security

This document tracks controls that are **implemented**. Planned controls for later phases (gateway
webhook dedupe, encryption of partner credentials) are specified in
[IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) and move here as they ship.

## Bookings and payments (Phases 4–5)

| Area                  | Control                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Price integrity       | The browser sends offer IDs and the total it showed; the server re-prices every offer from the provider and refuses (`PRICE_CHANGED`) if the total differs. Stored amounts come from the server, never the client                                                                                                                                                                                                           |
| Payment amount        | Payment orders are created for the booking's stored total; the client cannot choose an amount                                                                                                                                                                                                                                                                                                                               |
| Payment verification  | A booking is confirmed only after the gateway signature (HMAC of order and payment IDs) verifies on the server, compared in constant time. Invalid signatures are refused and audited (`PAYMENT_SIGNATURE_INVALID`). The browser's claim of success is never trusted                                                                                                                                                        |
| Idempotency           | `POST /flights/book` and `POST /buses/book` require an `Idempotency-Key`; the key is checked before booking and again if booking fails (a concurrent retry may have won); `(user, key)` is unique in the database, so retries and concurrent duplicates return one booking. Payment orders are reused per booking; payment and booking transitions are conditional updates, so a replayed verification cannot confirm twice |
| Bus seats             | Each seat is a row in `bus_seat_bookings` with a unique `(trip, seat)` constraint, written in the booking transaction, so two customers can never hold the same seat (tested with concurrent requests). Ladies-only seats are enforced on the server                                                                                                                                                                        |
| Overselling           | Seats are taken with one conditional `UPDATE … WHERE sold + n <= capacity` inside the booking transaction; a concurrency test books the last seat from three users at once                                                                                                                                                                                                                                                  |
| Holds                 | Unpaid bookings expire after `BOOKING_HOLD_MINUTES`; confirmation requires the hold to be valid in the same transaction. A payment captured after expiry is recorded as refund due (`PAYMENT_REFUND_DUE`) and never confirms released seats                                                                                                                                                                                 |
| Access                | Bookings, tickets and payments are visible only to their owner (others get `404`, so references cannot be probed) or staff with `booking:read:any`. All booking and payment routes require `booking:create` / `booking:read:own`                                                                                                                                                                                            |
| Development providers | `FLIGHT_PROVIDER=mock` (fictional airlines), `BUS_PROVIDER=mock` (fictional operators) and `PAYMENT_PROVIDER=mock` are refused in production. The mock checkout route is not mounted in production. Demo bookings are flagged and their PDF tickets watermarked "not valid for travel"                                                                                                                                      |
| Card data             | Never reaches ZPROO GO servers (the gateway's checkout collects it); nothing card-related is stored or logged                                                                                                                                                                                                                                                                                                               |
| Audit                 | `BOOKING_CREATED`, `PAYMENT_ORDER_CREATED`, `PAYMENT_CAPTURED`, `PAYMENT_FAILED`, `PAYMENT_SIGNATURE_INVALID`, `PAYMENT_REFUND_DUE`                                                                                                                                                                                                                                                                                         |

## Authentication (Phase 2)

| Area                  | Control                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Passwords             | argon2id (19 MiB, t=2, p=1 — OWASP minimum; parameters stored per hash so they can be raised). Policy: 8–128 chars, letters and numbers. Unknown accounts still run a hash comparison, so response time does not reveal whether an account exists                                                                                                                                                      |
| OTP                   | 6 random digits (`crypto.randomInt`), valid 5 minutes, 5 attempts, single use, only the newest code works. Stored as HMAC-SHA256 bound to purpose and target, keyed from `JWT_SECRET`, so a leaked table is useless. Sign-in codes cannot reset passwords                                                                                                                                              |
| Account discovery     | `send-otp` and `forgot-password` answer identically for registered and unknown numbers/emails; password login gives one message for wrong password and unknown account                                                                                                                                                                                                                                 |
| Access tokens         | JWT HS256, 15 minutes, `iss`/`aud`/`exp` verified, algorithm pinned, unique `jti`. Held only in memory by the web app (never `localStorage`)                                                                                                                                                                                                                                                           |
| Refresh tokens        | 256-bit random, stored as HMAC-SHA256 (`JWT_REFRESH_SECRET`). `HttpOnly`, `SameSite=Lax`, `Secure` in production, `Path=/api/auth`. Rotated on every use (atomic conditional update, so concurrent refreshes cannot both win). Replaying a rotated token revokes the whole session and writes an `AUTH_REFRESH_REUSE` audit entry. The web app serialises refreshes across tabs with the Web Locks API |
| Session ending        | Logout revokes the device's session; "sign out of all devices" and password reset revoke every session; suspended users are refused at login and on refresh                                                                                                                                                                                                                                            |
| CSRF                  | The only cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) rely on `SameSite=Lax` (cookie not sent on cross-site POSTs) plus the CORS allowlist. All other endpoints need the bearer token, which browsers never attach automatically                                                                                                                                                   |
| Signup token          | Proof of phone ownership after OTP: JWT with its own audience (cannot be used as an access token), 15 minutes. Registering twice with it returns 409                                                                                                                                                                                                                                                   |
| Social sign-in        | Google/Apple ID tokens verified against the provider's JWKS (signature, issuer, audience, expiry). Existing accounts are linked only when the provider says the email is verified                                                                                                                                                                                                                      |
| Authorization         | `authenticate` + `authorize(permission…)` middleware; permissions come from the roles in the **verified** token, resolved server-side from the database (cached 60 s). Role changes take effect at the next refresh (≤ 15 minutes). The web UI's guards are convenience only                                                                                                                           |
| Mass assignment       | Request bodies are parsed with strict schemas; `PATCH /me` only accepts `fullName`, so roles and status cannot be set by users                                                                                                                                                                                                                                                                         |
| Redirects             | Post-login `?next=` accepts same-site paths only                                                                                                                                                                                                                                                                                                                                                       |
| Brute force           | Per-account login limit (10 / 15 min), per-number code limits (1 / min per flow, 5 / hour), per-IP auth limit (generous because of carrier-grade NAT), all shared through Redis. Rate limiting fails open if Redis is down; OTP attempts stay capped in PostgreSQL                                                                                                                                     |
| Development providers | `SMS_PROVIDER=console` / `EMAIL_PROVIDER=console` print codes to the terminal (stderr, not the structured log) and return `devCode` in responses. Environment validation refuses both in production                                                                                                                                                                                                    |
| Audit                 | `AUTH_REGISTER`, `AUTH_LOGIN` (method), `AUTH_SOCIAL_LOGIN`, `AUTH_SOCIAL_LINKED`, `AUTH_PASSWORD_RESET`, `AUTH_LOGOUT_ALL`, `AUTH_REFRESH_REUSE`, `USER_PROFILE_UPDATED`, with IP, user agent and request ID. A failed audit write never blocks the user                                                                                                                                              |

Before going live, a real SMS provider adapter is required (production refuses the console provider).

## Platform (Phase 1)

| Area                | Control                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Configuration       | Zod-validated env at boot; production refuses to start without distinct ≥32-char JWT secrets; config errors never print values                                                                                                                                                                                                                              |
| Secrets             | `.env` git-ignored; only `VITE_*` values reach the browser; no secrets in the repo                                                                                                                                                                                                                                                                          |
| HTTP headers        | Helmet: `default-src 'none'` CSP for JSON responses (relaxed only under `/api/docs`), HSTS, `nosniff`, `frame-ancestors 'none'`, same-site CORP; `X-Powered-By` removed                                                                                                                                                                                     |
| CORS                | Explicit origin allowlist (`CORS_ORIGINS`), credentials allowed only for listed origins                                                                                                                                                                                                                                                                     |
| Rate limiting       | Per-IP limit on `/api` with standard `RateLimit` headers, shared across instances through Redis (see Authentication for per-route limits)                                                                                                                                                                                                                   |
| Input               | JSON bodies capped at 100 kB; malformed JSON → 400; `validate()` middleware with shared Zod schemas                                                                                                                                                                                                                                                         |
| Errors              | Unknown errors return a generic message and `INTERNAL_ERROR`; stack traces and internals are only logged                                                                                                                                                                                                                                                    |
| SQL injection       | Prisma parameterised queries only; raw SQL must use tagged templates (`$queryRaw\`…\``)                                                                                                                                                                                                                                                                     |
| Logging             | Structured JSON (Pino) with request ID, method, path, status and duration. Query strings are dropped (PII). Redacted: `authorization`, `cookie`, `set-cookie`, Razorpay signature, and any `password`, `passwordHash`, `otp`, `otpCode`, `token`, `accessToken`, `refreshToken`, `secret`, `signature`, `cardNumber`, `cvv` field. A test asserts redaction |
| Data at rest        | Schema stores only hashes of refresh tokens and OTPs                                                                                                                                                                                                                                                                                                        |
| Authorization model | Permission keys and role grants are defined once in `@zproo/types` and seeded into the DB; the API enforces them on every request (the web UI only hides controls)                                                                                                                                                                                          |
| Web                 | React escapes output by default; no `dangerouslySetInnerHTML`; admin routes are `noindex` and disallowed in `robots.txt`                                                                                                                                                                                                                                    |

## Dependency audit

`npm audit` reports no known vulnerabilities at the time of writing. A high-severity `deepmerge-ts`
advisory in Prisma's CLI config loader is resolved by an npm `overrides` entry
(`deepmerge-ts@^8`) in the root `package.json`.

## Reporting

Report suspected vulnerabilities privately to the maintainers. Do not open public issues for
security problems.
