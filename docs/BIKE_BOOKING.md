# Bike Booking (UI, mock data)

Scope of this release: **landing → results (filters) → bike details**. The booking checkout
(customer details, summary, confirmation) is the next milestone. "Book Now" validates the
rental dates and opens a recap dialog; nothing is reserved and no payment is taken.

## Routes

| Route             | Page                  | Purpose                                                          |
| ----------------- | --------------------- | ---------------------------------------------------------------- |
| `/bikes`          | `BikesPage`           | Search card, categories, popular bikes, how it works, hubs, FAQs |
| `/bikes/results`  | `BikeResultsPage`     | Search box, rental summary, filters, sort, bike cards            |
| `/bikes/locations`| `BikeLocationsPage`   | All pickup / return hubs                                         |
| `/bikes/:id`      | `BikeDetailsPage`     | Gallery, specs, charges, policies, hubs, reviews, FAQs, similar  |

Filters live in the URL (`?q=&cat=&tr=&max=&avail=&sort=`) so results can be shared and survive
back/forward. Category tiles link to `/bikes/results?cat=<category>`.

## Folder structure

```
apps/web/src/
  pages/bikes/              route components only (compose features/bikes)
  features/bikes/
    types.ts                domain types (mirror the future API shapes)
    api.ts                  the ONLY file that knows where data comes from (mock today)
    hooks.ts                TanStack Query hooks over api.ts
    mock/                   bikes.mock.ts, locations.mock.ts, reviews.mock.ts
    content.ts              static copy (features, how-it-works, FAQs)
    rules.ts / pricing.ts   placeholder business rules and the quote calculator
    filters.ts / validation.ts / dates.ts / store.ts / links.ts
    components/             BikeCard, BikeFilterPanel, BikeGallery, BikeSearchPanel,
                            ResultsSummaryBar, CategoryTiles, ReviewsSection, SimilarBikes,
                            FaqList, FeatureCards, LocationCard, PriceBreakdown,
                            ScheduleFields, BookNowDialog, ui.tsx (states and fields)
```

Reused from the rest of the app: `TravelHero`, `Section` / `SectionHeader` / `Rail`,
`SearchButton`, `Seo`, and the `@zproo/ui` primitives (Button, Badge, Card, Dialog, Skeleton).
The home page "Bikes" search tab now renders the same `BikeSearchPanel`.

## Backend integration (later)

Only `features/bikes/api.ts` changes. Keep the signatures and swap each body for a call through
`@/services/http`:

```
listBikes(filters)   → GET /bikes
getBike(id)          → GET /bikes/:id
listLocations()      → GET /bike-locations
listReviews(bikeId)  → GET /bikes/:id/reviews
createBooking(req)   → POST /bike-bookings        (used by the next milestone)
```

No fake endpoints are created. Pricing in `pricing.ts` / `rules.ts` is a placeholder until the
rental business rules are signed off.

## UI states

Loading (skeleton cards, details skeleton, review skeleton), empty results (with "clear
filters"), error with retry (landing, results, details, hubs, reviews), and form validation on
the rental schedule. To see error states without a backend add `?mockError=1` to a `/bikes`
URL (`?mockError=notfound` for a 404 on the details page).

## Images

Three WebP views per bike plus a hero banner, generated by `scripts/generate-bike-art.mjs`.
They are original illustrations, not photographs. To use licensed photos, replace the files in
`public/assets/bikes` keeping the names (`<bike-id>-1..3.webp`, 960 × 640). See
`public/assets/bikes/README.txt`.

## Testing

`features/bikes/bikes.test.ts` covers mock-data integrity (including that every image exists),
pricing, filters, validation and links. Run `npm run test -w @zproo/web`.
